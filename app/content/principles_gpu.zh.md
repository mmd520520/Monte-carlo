#### 为什么 GPU 适合蒙特卡洛

- **光子之间互不影响**：第 1 个光子怎么走，和第 2 个毫无关系。这种问题叫“天然可并行”（embarrassingly parallel）：同时干活的人越多，算得越快。
- **CPU 和 GPU 擅长的事不一样**：CPU 是少数几个“全能大核”，擅长复杂、分支多的工作；GPU 是成千上万个“简单小核”，擅长大量重复的简单计算。追踪光子的每一步（抽随机数、算距离、乘一个指数、换方向）都很简单，正好适合 GPU。
- **所以 GPU 的做法是一个线程追踪一个光子**，几万个光子同时在组织里走；CPU 版是一个核一批光子，14 个核同时走 14 个。

#### 放到 GPU 上要解决的四个问题

| 问题 | 为什么会出现 | 常用解法（MCX 的思路） |
|---|---|---|
| 路径分叉（divergence） | GPU 每 32 个线程一组（warp），同一时刻只能执行同一条指令（SIMT）。一个光子在散射、另一个在过边界，就只能轮流执行，另一部分线程在等 | 每一步写得尽量统一、少分支；一个线程追完一个光子马上发射下一个（persistent threads），不让线程空着 |
| 写冲突 | 几千个线程同时往同一个三维网格里加能量，光源附近的体素尤其拥挤，普通加法会“写丢” | 原子加法（atomic add）：硬件保证每次加法完整完成。CPU 版每个核一份网格，GPU 的显存放不下几千份 |
| 随机数 | 每个线程都要有自己独立、互不相关的随机数序列 | 每个线程一个很小的随机数发生器（MCX 用 xorshift128+，状态只有 16 字节），种子各不相同 |
| 精度 | GPU 的单精度（float32）快得多，消费级显卡的双精度很慢 | 计算主要用单精度；能量守恒等总量要单独检查误差 |

#### 和我们 CPU 版的区别

- **可复现性**：GPU 上原子加法的先后顺序每次不同，结果的最后几位会有微小差别（统计上等价）。我们的 CPU 版是逐位一致的。所以 GPU 结果要按“在统计误差内一致”来验收，不能要求每一位都相同。
- **单位**：MCX 输出的是每单位进入组织能量的光注量，要乘 `flux × tstep × energytot / nphoton` 才是我们的单位。这个换算已经在 Mac 上实测核对过。
- **速度从哪来、卡在哪里**：光子越多、每一步越简单，GPU 的优势越大。主要瓶颈是光源附近的写冲突、路径分叉和显存带宽。

#### 可行性测试（2026-11-07）

用美国东北大学方倩倩（Qianqian Fang）教授的 MCX-CL，在同一台 Mac 的 GPU（20 核）上跑同一个平板：10⁷ 个光子 0.4 秒；我们的引擎 14 核 CPU 4.8 秒，大约快 12 倍。吸收比例都是 0.2784，与加倍法相同。MCX 官方说法是在 NVIDIA 显卡上比优化过的 CPU 程序快几百倍，要用自己的机器实测。

#### 现在的决定：暂缓

2026-11-08 决定 GPU 加速先不做：先补全模型（皮肤、脂肪层），做 CPU 侧的优化（“优化方向”里的 S1、S3、S5）。等到常规需要 10⁸ 以上的光子，或者要反复扫参数时，再按 [GPU 接入指南](https://github.com/mmd520520/Monte-carlo/blob/refactor/python-interactive/project/public/gpu_mcx/GUIDE.md)（`project/public/gpu_mcx/GUIDE.md`）接入：

1. 先做“后端”接口：同一个模型可以选 CPU（现在的引擎）或 GPU（MCX）来算，结果格式完全一样。
2. 每个模型都用加倍法和现有引擎交叉验证过才能用。
3. MCX 是 GPLv3 许可，只能作为可选安装，不打包进我们的代码。
4. 先确定机器（NVIDIA 显卡），实测之后再定。
