# 05 隐私和安全：什么能公开、什么不能

> 结论：推上公开仓库的东西收不回来——删掉文件，git 历史里还在，别人可能已经下载。所以“能不能公开”要在动手之前判断，并且用自动检查兜底。

## 三层存放

| 放在哪 | 放什么 | 谁能看 |
|---|---|---|
| 公开仓库（`project/public/`、代码、`docs/` 等） | 代码、技术文档、可公开的方案和调研 | 所有人 |
| 私有空间（`project/private/`，存企业微信微盘） | 内部讨论、分享材料、和人有关的文档、产品相关的讨论 | 微盘里共享的几位同事 |
| 只在本地（`references/`、`outputs/`） | 第三方资料（版权不归我们）、可以重新生成的运行结果 | 自己；需要时另行共享 |

`project/private/`、`references/`、`outputs/` 都写在 `.gitignore` 里，git 不会收录。

## 一份东西该放哪：按顺序问

1. 有没有**个人信息或对人的评价**？（照片、简历、联系方式、绩效、工作评价）→ 私有
2. 有没有**产品规划、客户、商业判断或未公开数据**？→ 私有
3. 有没有**公司内部的流程、权限、账号或平台安排**？→ 私有
4. 是不是**别人的版权材料**？（论文 PDF、别人的 PPT）→ 不进 git
5. 有没有**密码、密钥、令牌**？→ 绝不进任何文件，放环境变量

都不是，而且能帮别人理解或使用代码 → 公开。**拿不准就先放私有**：从私有挪到公开容易，反过来做不到。

## 自动检查：推送保护

光靠记性会出错，所以加了一道自动检查（`tools/pre-push`）：每次推送前检查**每一个**要推上去的提交，含私有文件夹、第三方资料或运行结果的，直接拒绝推送。每台电脑装一次：

```bash
cp tools/pre-push .git/hooks/pre-push && chmod +x .git/hooks/pre-push
```

为什么要检查每一个提交而不只是最新的？因为中间某个提交里有过的文件，推上去之后在历史里一样看得到。

## 已经进了提交，还没推送

这个项目真的遇到过：一份内部文档已经进了几个提交，推送前发现。

- 只删文件、再提交一次——**不够**，旧提交里还在。
- 正确做法：改写那几个提交的历史，把文件从每个提交里去掉，再推送。改写前先备份原分支。
- 已经推送到公开仓库的：当作已经泄露处理（密钥立刻作废），再改写历史；别人手里的副本收不回来。

## 用 AI 工具和在线服务时

| 场景 | 规则 |
|---|---|
| AI 编程工具读公开代码 | 可以 |
| 把私有文档、产品细节、未公开数据粘贴给 AI | 只用公司批准的工具；拿不准就不贴 |
| 在线计算服务、云 GPU | 只放公开的模型和参数 |
| AI 生成的内容 | 发出去之前，人名、数字、日期由人核对 |

## 分享时

- 网页、在线文档的链接默认是私有的；分享给谁、能不能转发，发之前想清楚。
- 公开文档提到私有材料时，只说“在私有空间”，不写具体内容。
- 给外部看的版本，单独做一份，不直接转内部文件。
