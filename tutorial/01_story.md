# 01 案例：从散落的文件到团队能用的工具

> 结论：问题不在于原型做得不好，而在于它只存在于一个人的电脑和脑子里。把它放进一个仓库、写清楚、加上测试，别人才能接手；AI 让这件事从几周缩短到一天。

## 起点：一个人闷头做出来的原型

光学研究员马孟帝用 MATLAB 做了两个蒙特卡洛光传输模型（皮肤血管、膝关节），能出结果。这是科研原型最常见的样子：

- 代码、结果图、安装包、论文、数据集都在本地和网盘里，分散在不同地方
- 皮肤和膝关节是同一套算法复制后各改各的，有 19 个同名文件
- 参数写在脚本中间，同一个光源有三种说法
- 没有总说明，也没有自动测试；怎么验证，只有作者自己知道

这不是谁的错：一个人赶进度时，这样最快。但它带来三个风险：**换人就断**、**结果没法复核**、**别人用不上**。

## 第 1 步：集中到一个仓库（11-06，一个下午）

把所有东西上传到一个 GitHub 仓库：14 次提交，3,045 个文件、494 MB。

- 好处：第一次有了“一个地方”，而且有时间记录。
- 问题：自写代码只有约 2 MB，其余是第三方源码、安装包、重复压缩包；没有入口，别人很难找到要看的东西。

**经验：先集中，再整理。** 集中这一步不需要完美。

## 第 2 步：先写方案，再动代码（11-07 上午）

在动任何代码之前，先写了一份重构指南：现状盘点（每类文件多大、哪些重复）、10 条原则、目标结构、分阶段计划、验收标准。人看过方案，AI 再按方案执行。

**经验：AI 执行得很快，所以方向错了也错得很快。** 方案是人把关的地方。

## 第 3 步：分阶段重构（11-07，7 个阶段）

| 阶段 | 做了什么 | 怎么证明没做坏 |
|---|---|---|
| 1 整理仓库 | 第三方资料、运行结果移出 git；每个文件夹写 README | 仓库从 494 MB 降到 2.4 MB |
| 2–3 搭引擎 | 一套 Python 引擎 + 两个参数预设，参数带文献出处 | 能量守恒误差 < 10⁻⁸ |
| 4 对比 | 和 MATLAB 原版的结果对比 | 各项在统计误差内一致 |
| 5 剂量 | 剂量计算和命令行 | 定义和原 MATLAB 一致 |
| 6 界面 | 网页交互界面 | 自动测试界面能跑 |
| 7 文档 | 算法说明、5 分钟上手 | 新人按 README 能跑起来 |

每个阶段一个提交，提交说明写清楚做了什么、为什么。

之后几天继续补：和独立的确定性算法（加倍法）对比，验证不再依赖 MATLAB；界面改成中英双语；调研了 GPU 加速。

**经验：小步走，每步都能运行、能验证。** 出了问题容易定位，也容易撤回。

## 第 4 步：分清公开和私有

重构过程中发现两件事：

- 内部分享的 PPT（含个人介绍）和内部文档不能进公开仓库
- 有一份内部文档已经进了几个待推送的提交。删掉文件不够，git 历史里还在；推送之前发现，改写了那几个提交的历史才推送

于是有了 `project/public/` 和 `project/private/` 两个文件夹，以及推送前的自动检查。详见 [05_privacy.md](05_privacy.md)。

**经验：推上公开仓库的东西收不回来。** 规则和自动检查要在第一次推送之前就有。

## 第 5 步：交给作者接手

重构是 AI 在一天里完成的，所以最后一步是让原作者核对和掌握：哪些判断需要领域知识确认、怎么在一两周内读懂新代码、怎么和产品结合。没有这一步，代码再整齐也只是“AI 写的东西”。

**经验：AI 可以写，但必须有人懂、有人负责。**

## 一个小插曲：人名写错了

一开始我们把作者的身份写错了（写成了“实习生”），出现在十几个文件里。改正之后，把“谁是谁”写进了 AI 的长期记忆和仓库说明里。

**经验：AI 不知道的事实会被它“合理地”补上。** 人名、职务、日期、数字，都要人来核对。

## 下一个项目

不用再走一遍“先散落、再集中、再重构”。从第一天就建仓库、写 README、分公开和私有，见 [07_new_project.md](07_new_project.md)。
